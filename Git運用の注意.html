Git運用の注意

チーム開発を円滑に進めるための絶対ルールとガイドライン

📌 開発の鉄則ルール

1. 「作業前に必ずPull」をチームの絶対ルールにする

他の人がコミットをプッシュしているのに、自分が古い状態のままコードを書いてプッシュしようとするとエラー（Non-fast-forward）になります。

【対策】 PCに向かってコードを書く前、席を外して戻ってきた時など、「何かする前はまず git pull」を合言葉にしてください。つねに最新のコードをベースに作業を始めるのが鉄則です。

2. コミットとプッシュは「小さく、細かく」

「機能が全部完成するまでプッシュしない」のは絶対にNGです。何日分もの変更をまとめてプッシュしようとすると、ほぼ確実に巨大なコンフリクトが発生し、修正に何時間も溶かすことになります。

【対策】 「関数を1つ作った」「画面のボタンを配置した」など、30分〜1時間単位の小さな単位でコミット・プッシュしましょう。他のメンバーにも自分の変更がすぐ伝わるため、衝突を最小限に抑えられます。

3. 「壊れたコード」は絶対にプッシュしない

mainブランチしかないので、あなたがプッシュしたコードは一瞬でチーム全員のパソコンに同期されます。もし動かないコード（エラーが出る、ビルドが通らないコード）をプッシュしてしまうと、チーム全員の開発がストップしてしまいます。

【対策】 プッシュする前に、必ず自分の手元で「正常に動作するか」「エラーが出ていないか」を確認（ローカルテスト）してください。未完成のコードをどうしても共有したい場合は、コメントアウトするか、処理を通らないように工夫しましょう。

4. 担当範囲（触るファイル）を明確に分ける

同じファイルの同じ行を複数人で同時に編集すると、100%コンフリクトします。

【対策】 毎朝のミーティングなどで、「誰がどのファイルを触るか」の縄張りをしっかり決めておくと安全です。
Aさん：トップ画面のHTML/CSS
Bさん：ユーザー登録の裏側処理（API）

このようにファイル自体が分かれていれば、同じmainブランチにどんどんプッシュしてもコンフリクトは起きません。

🛠️ 万が一、コンフリクト（衝突）が起きたら？

気をつけていてもコンフリクトは起きます。その時の心構えです。

「絶対に1人で勝手に直さないこと！」

Gitが「どっちのコードを残せばいいか分からない！」と言っている状態なので、勝手に判断して相手のコードを消してしまうとトラブルになります。必ず衝突した相手と一緒に画面を見ながら「どっちのコードを残すか（あるいは混ぜるか）」を話し合って修正してください。

💡 チームを救う「コミュニケーション」のコツ

テクニカルなこと以上に大事なのが、チーム内での声かけです。

「今から〇〇のファイルを修正してプッシュするよ！」
「大きな変更プッシュしたから、みんな一回 pull して！」

チャットツールや口頭で、これらを一言かけ合うだけで、Gitのトラブルは8割減らせます。

# コメントの形式

できれば半角で入力

Gitコメントは以下のようなプレフィクスをつけるのが一般的です。以下を参考にコメント品質を保つようにして下さい。

add 意味: 新しいファイル、機能、ライブラリなどを追加した場合。
【例】
add: ログイン画面のファイルを追加
add: 日付計算用のライブラリを追加
update 意味: 既存の機能、仕様、設定などを変更・更新した場合。
【例】
update: パスワードの文字数制限を8文字から12文字に変更
update: READMEの環境構築手順を最新化
delete del remove
意味: 不要になったファイル、機能、コードを削除した場合。
【例】
del: 使われていない古いアイコン画像を削除
remove: デバッグ用の不要なコンソール出力を削除
fix 意味: バグやエラー、意図しない挙動を直した場合。
【例】
fix: スマホで見たときに文字が見切れる不具合を修正
fix: 存在しないページにアクセスするとエラーになる問題を修正
clean 意味: コードの動作は変えずに、見やすく整理（リファクタリングやフォーマット）した場合。
【例】
clean: 処理が長かったため、関数を分割して整理
clean: ソースコード内のインデントと改行を整える
rename 意味: ファイル名や、変数名・関数名などを変更した場合。
【例】
rename: ユーザー画像フォルダの名前を img から images に変更
move 意味: ファイルやフォルダの場所を移動させた場合。
【例】
move: 共通設定ファイルを config フォルダ配下に移動
